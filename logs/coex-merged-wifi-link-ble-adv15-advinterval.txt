板子 BLE 广播的空口间隔，工作站 HCI 监视器的读数（2026-11-27，合并镜像 ble-adv15 轮）

怎么量的：板子跑合并镜像 -Dcoex-ble-adv（最终代码，sha256 0e9d7a8d8658084f8e86a5ab767c82d58f009f50ac77797dc4ca6acda0824bd9，与 logs/coex-merged-wifi-link-ble-adv13-boot.log 同一个镜像；27/27），
工作站在广播窗口里用 bluez 5.86 的 btmon（要 root）记 HCI 事件，同时 bluetoothctl 进 scan 子菜单先 duplicate-data on 再 scan on（配方在 tools/ap-side/README.md 的「蓝牙一侧」）——这样内核下发 LE Set Extended Scan Enable 时 Filter duplicates = Disabled，
同一个广播者的每一次广播事件都会上报（默认扫描是 Enabled，56 秒只上报一两次）。板子的镜像与 HCI 命令没有变：间隔仍是 LE Set Advertising Parameters 里写的 0x00A0。
btmon 的时间戳是它起算后的秒数；一块 HCI Event 就是一次广播事件被扫描窗口碰到的记录。

结论：19 段按 100 ms 都有解（全部），按 200 ms 有解的只有 5 段。空口上的广播间隔是 100 ms（含 advDelay 平均约 105 ms）。
LE Set Advertising Parameters 的间隔字段是 0.625 ms 一档，0x00A0 = 160 x 0.625 ms = 100 ms；此前注释里按 1.25 ms 一档算出的 200 ms 是错的。
最直接的一段是最上面那条：相邻两次广播事件相隔 103.9 ms（100 ms 加 3.9 ms 的 advDelay），200 ms 的解释放不下它。

为什么只有 19 段：上报很稀（约 1.2 次/秒，其他邻居合计也只有每秒几条），扫描窗口碰不到大部分广播事件；
原因没有查（工作站这块 Intel Wi-Fi/蓝牙 combo 的天线同时忙着 Wi-Fi 是一个猜测）。稀疏不影响上面的判断——每一段都要能凑成整数倍。
